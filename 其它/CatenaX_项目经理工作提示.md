## 1. 你在这个项目里真正要守住的三件事

1. **指导，不是代建。** 西门子负责方案、指导、验证方法和交付物；客户动手部署、备环境、出数据、做安全评审、执行备份。现场一旦变成“西门子工程师替客户把集群搭完”，进度看起来快，验收和运维会反噬。
2. **固定范围、固定费用。** 方案确认书签字后，改架构或加需求必须走变更。结项确认书签字后的新功能是二次需求，不在本期报价内。
3. **四个签字比五十张幻灯片重要。** 合同关口是四份《服务确认书》：方案、生产上线、护照设计、结项。没有签字，不要假装阶段结束。

西门子对联合项目团队享有**主要项目管理权**（SOW §6.3）：进度/质量偏差经双方确认后，可以要求增加或更换低绩效成员。这个权力要用在“保障交付”，不要用在日常指责。

## 2. 上任第一周必做（不要直接开始画架构图）

按顺序做完再进入大规模调研访谈：

| 序号 | 动作 | 完成标准 | 落到哪 |
| --- | --- | --- | --- |
| 1 | 召开启动会 | 纪要发出，红线与变更流程被宣贯 | 计划 `03_WBS` 的 1.0 |
| 2 | 锁定组织 | 指导委员会、双方 PM、CCB、业务/IT/安全/数据接口人有名单和备份人 | `07_沟通与会议` |
| 3 | 发出客户前置清单 | 客户 PM 书面认领 C-01～C-18 | `06_客户前置条件` |
| 4 | 核验 Onboarding 与 Submodel Server | 每条“通过”或“缺口+责任人+到期日” | 前置 C-03、C-08 |
| 5 | 确认例会日历 | 建议每周五 30–45 分钟；指导委员会每月固定日 | `07` |
| 6 | 确认现场与数据红线 | 坑梓深圳办公室；调试必须客户审批、监督、留日志 | SOW §3.3、§4 |
| 7 | 打开风险单 | 过一遍 R-01～R-25，删不适用、补现场新风险 | 风险登记册 |

第一周结束时，你手里应该有三份“活文件”：计划状态、前置缺口、风险清单。缺任何一份，都还没进入可控状态。加速基线下，**周五就要签 M1**，所以启动会当天必须发出方案验收通知。

## 3. 每周节奏（建议周五例会）

例会前半天，西门子 PM 更新：

1. `03_WBS详细计划` 的状态 / 实际开始 / 实际结束
2. `08_问题与行动项` 的开放与逾期项
3. `06_客户前置条件` 的缺口
4. 风险单里所有“高”且“开放”的风险
5. `10_周报模板`（可直接贴进邮件）

例会只讨论四类事：**偏差、缺口、决策、下周关门点**。不要把例会开成技术分享会。

状态规则：

- **阻塞**：必须在 08 表建单，并判断是否升级或提变更
- **黄灯**：有偏差但仍能在里程碑内消化
- **红灯**：里程碑日期受威胁，或出现范围争议

## 4. 四个里程碑怎么收（照着做）

SOW 原文把里程碑放在第 2 / 7 / 10 / 12 周、共 58 个工作日。**当前执行基线已加速为约 27 个工作日、6 个项目周**（2026-08-17～09-22，赶在中秋前结束）。四个确认书和九项交付物一个不少，只是窗口更紧。启动日若变，按工作日整体平移。

加速带来两条必须在启动会书面确认的事：

- M1 通知期不足 5 个工作日：启动会当天发出书面“可供验收”通知，并请客户确认接受。
- 节点会当场签收。不要把 §7 的 10 个工作日默认验收当成进度策略；27 天里等不起。

### 共同动作（每个里程碑都做）

1. **提前至少 5 个工作日**书面通知“交付物可供验收”（§7.2.1）
2. 把材料按附件 A 打包，不要缺一份再强推签字
3. 召开节点会，预填《服务确认书》，会上签
4. 扫描件当天归档，原件按公司规定保存
5. 不要把“客户 10 个工作日不拒绝即视为接受”当成计划缓冲。那是保护条款，不是进度策略
6. 客户投入正式使用也可视为接受，记得留证据（生产流量、业务邮件）

### M1 方案确认书（交付物 #1）

- 方案必须能让客户去备货：最低规格、双环境、已知限制、客户待办
- 签字后方案即实施基线。有人说“再改一改架构”，先停实施，再提 CR

### M2 生产环境确认书（交付物 #2–#6 一起）

这是最容易翻车的关口。附件 A 写得很清楚：生产上线阶段要签的是 **#2 测试上线、#3 Submodel、#4 观测、#5 安全、#6 生产**。缺任何一份都不要假装 M2 完成。

特别检查：

- 测试和生产报告分开，禁止用测试集群冒充生产
- Submodel Server 必须是客户已有且符合 CX-0002，本期不新建
- 安全评审由客户完成；西门子交四件套（SBOM、License、镜像扫描、安全配置说明）
- 提供/消费 + DTR 经 EDC 可访问，才是验收描述，不是“组件 Running 就算”

### M3 护照设计确认书（交付物 #7、#8）

- 灾备是指南，不是西门子替客户做日常备份
- 对接设计**不含代码实现**。纪要里写一句：设计已验收 ≠ 对接功能已上线
- 客户若当场要开发，引导去变更/新合同，不要口头答应“我们顺手写了”

### M4 结项确认书（交付物 #9）

- 手册 + 培训记录齐
- 培训对象是客户技术人员，不是全部最终用户
- 会上完成陪伴期交接，并声明结项后新增/改动为二次需求

## 5. 范围防火墙（会议上的标准答法）

遇到下面这些要求，先说“这超出本期 SOW，我帮你评估变更影响”，不要先说“可以”。

| 客户说法 | 合同事实 | 你怎么回 |
| --- | --- | --- |
| 官方组件有 bug，你们改一下 | 西门子不二次开发修复，只向官方反馈，不承诺修复时间 | “我们按约定提官方缺陷。修复后的迭代部署我们可以指导。” |
| 你们帮我们把数据从产线采出来 | 不负责具体数据收集 | “数据由贵方提供。数据不到，可以用假设数据验收，或按合同顺延。” |
| 顺便把 MES / 另一个系统也接上 | 未列明接口须变更 | “请提变更，5 个工作日内评估工期和费用。” |
| 帮我们装一套别的中间件 | 非必须第三方由客户负责 | “贵方协调安装，我们配合联调。” |
| 做一下压测 | 不负责压测 | “可以配合，但工具和额外人天在范围外。” |
| 集群太慢你们调优一下 | 只提规格，不负责调优 | “我们给规格和建议，实施由基础设施团队做。” |
| 给所有最终用户培训 | 只做集中知识转移 | “我们培训贵方技术人员，对内转训由贵方项目组完成。” |
| 把护照对接代码写完 | 附件 B：不含代码实现 | “本期交付设计指导书。开发需要新的范围。” |
| 结项后继续驻场做新功能 | 陪伴期是 5×12 远程支持 | “陪伴期按故障响应提供。新功能另立需求。” |

陪伴期边界（结项后 12 个月）：

- 工作日 5×12，收到请求后 1 小时内响应
- 默认远程（VPN / 电话 / 邮件）；现场须按紧要程度双方同意
- 向官方反馈功能缺陷的次数不超过 12 次

## 6. 客户依赖：什么时候该升级，什么时候该提变更

客户不按时完成前置，合同允许你改总进度（§5 开篇、§9）。不要靠团队加班“消化”客户延误，那会把责任边界搅浑。

建议阈值：

| 情况 | 动作 |
| --- | --- |
| 单一缺口，3 个工作日内能关闭 | 08 表行动项，例会跟踪 |
| 缺口关闭日已过，下一任务受阻 | L2：双方 PM 会见；书面确认新日期 |
| 再 3 个工作日仍无解 | L3：指导委员会；同步准备 CR（顺延 / 费用） |
| 数据不合格要西门子洗数、加接口、改流程 | 直接建 CR，不要先做再补手续 |
| 争议期间 | 继续交付**不在争议范围内**的服务（§6.5） |

指导委员会必须能在 **3 个工作日**内决策。名单里没有代理人，等于这个机制是空的。

## 7. 变更怎么走（§9）

1. CR 必须写清：改什么、根因、对范围/进度/费用的影响
2. 提出方 PM 先复核，再提交对方
3. 对方 PM + CCB 复核：进一步研究或拒绝
4. 西门子在 **5 个工作日**内评估时间与额外收费
5. 双方 PM 确认后签补充协议（人天单价按主合同），再纳入基线
6. **未签字的 CR 不实施**

CCB 成员在启动会上确认，不要等到第一份 CR 出现再找人。

计划工作簿 `09_变更记录` 已列出 SOW 原文中的典型触发情形，出现即建单。

## 8. 数据与安全红线（比进度更优先）

SOW §3.3 写得很硬：

- 系统中存储、处理、生成的全部数据归客户
- 未经客户书面授权，不得访问、复制、分析、导出、用于模型训练或任何其他目的
- 调试和运维必须通过客户审批，在客户监督下进行，并留日志

项目经理要做的具体事：

- 启动会把这条念出来，写进纪要
- 为现场/远程操作建“审批—执行—日志”最小闭环
- 禁止把客户数据拷到个人电脑或非客户指定环境
- 假设数据验收时，也要客户书面同意“可以用这份数据验收”

安全评审本身是**客户责任**。你的职责是按时交出加固材料，并推动评审给出“通过”或“带风险接受”，不要替客户安全部做签字。

## 9. 技术实施时你要盯的几个“假完成”

| 看起来做完了 | 合同上还没做完 |
| --- | --- |
| 四个 Pod 都是 Running | 尚未证明提供/消费，以及 DTR 经 EDC 可访问 |
| 测试环境跑通了 | 生产环境还没关门、没晋升、没单独出报告 |
| 监控装上了 | 没有告警规则，或组件未提供的日志被承诺“一定采到” |
| 镜像扫过了 | 没有 SBOM、License 单、安全配置说明，或客户评审无结论 |
| 说了 HA | Vault 自动 unseal、Node 扩容未被云平台支持，且方案没改成手动/不依赖 |
| 对接设计写完了 | 被理解成代码已交付 |

官方组件缺陷：只记录、只反馈、不私自改源码。陪伴期内把反馈次数记在风险单备注里，避免超过 12 次还在“顺手再提”。
