# database — 公开数据集分支 / Public-dataset branch

本目录是**公开算例**这一支的唯一入口。它与自造受控算例那一支严格分家:

This directory is the only entry point for the **public-instance** branch. It is kept strictly separate from the self-generated controlled-instance branch:

| 用途 / Role | 自造受控算例(原有) / Self-generated controlled instances (existing) | 公开数据集(本分支) / Public datasets (this branch) |
| --- | --- | --- |
| 算例 / Instances | `input/`、`input/ext/` | `database/json/` |
| 运行输出 / Run output | `output/` | `output_database/` |
| 汇总 CSV / Summary CSV | `experiments/` | `experiments_database/` |

分家的理由有两条,都不是洁癖。其一,`main.py` 的默认 glob 是 `input/*.json`,把上百个
公开算例放进去会让默认运行从跑 2 个算例变成跑 100 多个。其二,两支的**报告口径不同**
(见下节的两个 regime),混在同一个 output 目录里迟早会被当作同一批数据引用——本项目
已经在跨批次引用上栽过一次(见论文结论二十四)。

The split has two reasons, and neither is tidiness. First, the default glob in `main.py` is `input/*.json`; dropping in more than a hundred public instances would turn a default run of 2 instances into a run of more than 100. Second, the two branches use **different reporting conventions** (the two regimes in the next section). Mixing them in one output directory would eventually get them cited as one batch — this project has already been burned once by cross-batch citation (see paper conclusion 24).

对应规格文档《异构资源柔性作业车间协同调度核心算法.md》第十二节:12.1 数据集评估、
12.2 第一层退化对标、12.3 第二层受控扩展、12.4 数据准备清单。

This corresponds to Section 12 of the specification document 《异构资源柔性作业车间协同调度核心算法.md》: 12.1 dataset assessment, 12.2 first-layer degenerate benchmarking, 12.3 second-layer controlled extension, and 12.4 the data-preparation checklist.

## 一、目录结构 / 1. Directory layout

```text
database/
  README.md                  # 本文件:总索引与流程 / This file: index and workflow
  MANIFEST.csv               # 逐文件来源/下载日期/SHA256/许可/状态(唯一可信清单) / Per-file source, download date, SHA256, license, and status (the only trusted inventory)
  raw/                       # 原始发布件,**只读,永不修改** / Original releases, **read-only, never modified**
    README.md                #   逐文件说明与原始下载链接 / Per-file notes and original download links
    <dataset_key>/           #   按数据集分子目录 / One subdirectory per dataset
    tjsp_toolset/            #   van Os 配套工具集(Lyu/Liu 布局的机读编码 + 解析源码) / van Os companion toolset (machine-readable Lyu/Liu layouts plus the parser source)
  json/                      # 转换为规格 3.1 JSON schema 的算例(转换器产物) / Instances converted to the spec 3.1 JSON schema (converter output)
    <dataset_key>/
  network/                   # 还原/数字化的路网模板(规格 12.4 第 3 项) / Reconstructed or digitized road-network templates (spec 12.4, item 3)
    <layout_name>.json
  refvalues/                 # 文献参考值表(best-known / 可证最优 / 各方法自报值) / Literature reference table (best-known / proven optimal / values reported by each method)
    README.md                #   列定义 / Column definitions
    <dataset_key>.csv
```

`raw/` 与 `json/` 的关系是**单向的**:`json/` 里的每个文件都必须能由 `raw/` 加转换器
重新生成,不允许手工编辑 `json/`。手改一个算例文件就等于凭空造了一个算例,而它看上去
仍像公开数据。

The relation between `raw/` and `json/` is **one-way**: every file under `json/` must be regenerable from `raw/` plus the converter. Hand-editing `json/` is not allowed. Editing an instance file by hand invents an instance that still looks like public data.

### 一个例外:只借拓扑的算例落在 `input/pub/` 而不是 `json/` / One exception: topology-only instances land in `input/pub/`, not `json/`

`raw/tjsp_toolset/` 下的布局文件有一种不同的用法:**只取路网拓扑,工件数据与边权仍由
本项目生成**。这类产物不算公开算例,因此**不**进 `json/`,而是落在 `input/pub/`
——它们在报告口径上属于自造受控算例那一支,只是布局出处被外部化了。
生成器为 `tools/gen_pub_layouts.py`,对账脚本为 `tools/check_pub_layouts.py`,
转录结果登记在 `algorithm/generator.py` 的 `PUB_LAYOUTS`。

Layout files under `raw/tjsp_toolset/` are used differently: **only the road-network topology is taken; job data and edge weights are still generated by this project**. Those products are not public instances, so they do **not** go into `json/`. They land in `input/pub/` and, for reporting, belong to the self-generated controlled branch; only the layout provenance is external. The generator is `tools/gen_pub_layouts.py`, the reconciliation script is `tools/check_pub_layouts.py`, and the transcription is registered in `PUB_LAYOUTS` in `algorithm/generator.py`.

之所以要这条例外:paper04 那一支研究的是执行期扰动,没有公开基准可换(公开族发布的都是
静态问题输入),但"布局是不是作者自己挑的"这一质疑仍然成立且可以单独解决。只把拓扑
外部化,既回应了这个质疑,又不至于因搬入公开族过低的运输/加工时长比而让争用现象消失。
口径与实测结果见 `STRC/experiments/pub_layouts/README.md`。

This exception exists because the paper04 line studies execution-time disturbances, and there is no public benchmark to swap in (the public families publish only static problem inputs). The objection that "the author picked the layout" still stands and can be answered on its own. Externalizing only the topology answers that objection without importing the public families' very low travel-to-processing time ratio, which would make congestion disappear. Conventions and measured results are in `STRC/experiments/pub_layouts/README.md`.

### 为什么 `lyu` 单独重要 / Why `lyu` matters on its own

它的原文问题描述是"布局由一张**双向网络**表示,但**每一段同时只能有一辆车通过**",
其冲突变量里专门有一项表示"另一辆车正从相反方向占用同一段"——这**逐字等于本项目的
假设 A6**(走廊双向排他、两方向共用一份占用)。同时它满足:每道工序可由若干台机器加工
且工时随机器而变(A3)、机器在 20 节点网络上分散摆放、原文自身就在**扫描 AGV 数量**
(对应车臂比因子族)。其解码流程亦同构:先空载段、再满载段,装载时刻取
`max(C_{i(j-1)}, CT_ij)`。

Its problem statement says the layout is a **bidirectional network**, but **only one vehicle may traverse a segment at a time**. One conflict variable specifically means "another vehicle occupies the same segment from the opposite direction" — that is **word for word assumption A6** of this project (a corridor is exclusive in both directions and both directions share one occupancy). It also satisfies: each operation can be processed on several machines with machine-dependent times (A3), machines are spread over a 20-node network, and the source itself **sweeps the AGV count** (the vehicle-to-arm ratio factor family). The decode flow is isomorphic: empty trip first, then loaded trip, and the load epoch is `max(C_{i(j-1)}, CT_ij)`.

因此在本分支里,`lyu` 是**唯一一个可以不做语义翻译就直接运行**的公开族;其余各族都需要
补一个原数据没有的量(见下节)。

In this branch, `lyu` is therefore the **only public family that can be run directly without a semantic translation**. Every other family needs a quantity the source data does not provide (see the next section).

### 为什么不用 van Os & Basten 的算例 / Why the van Os & Basten instances are not used

`vanos2026exact` 的 CFTFJSSP 是同一问题类且有可证最优值,但其假设"只有装货站与卸货站
允许多车同时在场",即**其余节点容量为 1**。这直接摧毁本项目引理 1(最早到达即充分)的
前提——"停靠位容量充裕且不占用通行资源"——从而单标签 Dijkstra 必须换成安全区间规划的
区间标签。也就是说,在其语义下运行本方法**替换的是下层路由算法本身,不是算例**。
它的正确用途是:作为"这批算例(源自 Lyu 2019 / Liu 2023)大致能好到什么程度"的量级参照。

The CFTFJSSP in `vanos2026exact` is the same problem class and has proven optima, but it assumes that "only the loading station and the unloading station may hold several vehicles at once", i.e. **every other node has capacity 1**. That destroys the premise of Lemma 1 of this project (earliest arrival is sufficient) — "parking spots have ample capacity and do not consume travel resources" — so single-label Dijkstra would have to be replaced by interval labels from safe-interval planning. Running this method under that semantics **replaces the lower-level routing algorithm itself, not the instance**. Its proper use is as a magnitude reference for "how good this batch (from Lyu 2019 / Liu 2023) can roughly get".

> **已核实(2026-08-18)**,答案是"两者都不是":`TUE-EE-ES/TJSP-toolset`(van Os 硕士论文的
> 配套软件)里的 Lyu 算例**拓扑忠实、边权是补的**,而且补的是**无向**单位步长,不是单向。
> 布局只存三行——网格尺寸、仓库与机器所在的网格节点号、被拆掉的边对,例如
> `5x5` / `1 3 10 11 14 17 23 25` / `(8 13) (19 20)`,整份文件 14–44 字节,**不含任何行程
> 时间**。边权在 `library/model_data.py` 里硬编码为 `1`
> (`dijkstra_graph.addEdge(e[0]-1, e[1]-1, 1)`),机器间时长由 Dijkstra 现算,故必然对称、
> 满足三角不等式。这不是实现层的省事:`vanos2026exact` 的模型定义里,单步时长本身就是一个
> **常量**(原文输入参数表写作 "(Uniform) duration of a single step"),即"每条边一个单位"
> 是其问题设定的一部分,不是它为了跑 Lyu 算例临时凑的。逐项核对的结论:六个布局与 Lyu 的 Figures 10–15 **逐节点逐边相同**
> (Layout 4 的两处缺边 8–13 与 19–20 精确对上),工件数据与 Table 7 **逐位相同**;
> **唯独单位边权是 van Os 的填补,不是 Lyu 的数据**。
>
> **Checked (2026-08-18)**: the answer is "neither". The Lyu instances in `TUE-EE-ES/TJSP-toolset` (the companion software of van Os's thesis) have a **faithful topology and filled-in edge weights**, and what is filled in is an **undirected** unit step, not a one-way edge. A layout stores only three lines — grid size, the grid node ids of the depot and the machines, and the removed edge pairs, for example `5x5` / `1 3 10 11 14 17 23 25` / `(8 13) (19 20)`. The whole file is 14–44 bytes and **contains no travel times**. Edge weights are hardcoded to `1` in `library/model_data.py` (`dijkstra_graph.addEdge(e[0]-1, e[1]-1, 1)`); machine-to-machine times are computed by Dijkstra, so they are necessarily symmetric and satisfy the triangle inequality. This is not an implementation shortcut: in the model definition of `vanos2026exact`, the duration of one step is itself a **constant** (the source input-parameter table writes "(Uniform) duration of a single step"), so "one unit per edge" is part of the problem setting, not something improvised to run the Lyu instances. Item-by-item, the six layouts match Lyu's Figures 10–15 **node for node and edge for edge** (Layout 4's two missing edges 8–13 and 19–20 match exactly), and the job data match Table 7 **entry for entry**. **Only the unit edge weight is van Os's fill-in, not Lyu's data**.
>
> 因此本节取数结论不变且更硬:第二组的边权仍须视为外部引入的假设,`toolset` 只能用于对账与
> 量级参照。它的附带价值是提供了 57 个算例的 LBBD 参考值(`experimental-results/`,900 s 预算
> 下 52/57 可证最优)——但那是**在 van Os 的单位边权口径下**的最优,不是 Lyu 的参照值。
>
> The data-taking conclusion of this section therefore stands, and more firmly: the second group's edge weights must still be treated as an externally introduced assumption, and `toolset` may be used only for reconciliation and as a magnitude reference. Its side value is the LBBD reference values for 57 instances (`experimental-results/`, 52/57 proven optimal under a 900 s budget) — but those optima are **under van Os's unit-edge-weight convention**, not Lyu's reference values.

## 三、两个 regime,以及各自的报告口径 / 3. Two regimes, and the reporting convention of each

同一份公开数据要生成两个版本的算例,后缀区分,**绝不混报**:

The same public data produce two versions of each instance, distinguished by suffix, and they are **never reported together**:

| 后缀 / Suffix | 配置 / Configuration | 用途 / Role | 口径 / Convention |
| --- | --- | --- | --- |
| `-ideal` | `conflict_free=False`,运输时间取理想最短路矩阵 t*,预约表禁用;`delta_return=0` / `conflict_free=False`; travel times are the ideal shortest-path matrix t*; the reservation table is disabled; `delta_return=0` | **第一层退化对标**(规格 12.2) / **First-layer degenerate benchmarking** (spec 12.2) | 与文献 best-known 的 gap(%) / gap (%) against the literature best-known |
| `-excl` | 还原/给定路网,走廊容量 1、半开时窗排他;`delta_return` 按原数据集约定 / reconstructed or given road network, corridor capacity 1, half-open exclusive windows; `delta_return` follows the source dataset | **第二层争用版本**(规格 12.3a) / **Second-layer congestion version** (spec 12.3a) | 本项目内部的四级阶梯比较 / the four-level ladder comparison internal to this project |

`-ideal` 档回答的是"我们的上层算法弱不弱"——这不是方法比较,而是排除**有效性威胁**
(论文局限(5):单一实现)。它必须报,而且应该报在实验设置一节而不是结果一节。

The `-ideal` mode answers "is our upper-level algorithm weak?" That is not a method comparison; it rules out a **validity threat** (paper limitation (5): a single implementation). It must be reported, and it belongs in the experimental-setup section rather than the results section.

`-excl` 档才是本项目贡献所在的设定。关键性质:**删去排他约束后 `-excl` 精确退化为
`-ideal`**(规格 5.4 与论文 §3.5),所以两档不是两个算例,是同一算例加/不加一族约束。

The `-excl` mode is the setting where this project's contribution lives. The key property is that **removing the exclusive constraints makes `-excl` degenerate exactly into `-ideal`** (spec 5.4 and paper §3.5), so the two modes are not two instances; they are the same instance with or without one family of constraints.

### 三之二、第三个用途:给自建算例的因子取值当锚(2026-08-18) / 3.2 A third use: anchoring the factor values of the self-built instances (2026-08-18)

上面两个 regime 都是"拿公开数据跑我们的算法"。还有一个用途不需要跑任何算法,却回答了一个
更难回答的问题:**自建算例的 H / F / T̄t/T̄p 凭什么取那几个值?**

The two regimes above are both "run our algorithm on public data". A third use runs no algorithm at all, yet answers a harder question: **why do the self-built instances take those particular values of H / F / T̄t/T̄p?**

`py -m tools.pub_features --csv` 用 `algorithm/instance.py` 的 `feature_params`——即生成器
落盘 `_features` 时调的**同一个函数**——把 20 个 `-ideal` 算例量一遍,产出
`experiments_database/pub_features.csv`。同函数同口径是这组数能当"锚"的**前提**:各算一套
再声明口径一致是不作数的。实测结果:

`py -m tools.pub_features --csv` uses `feature_params` in `algorithm/instance.py` — the **same function** the generator calls when it writes `_features` — to measure the 20 `-ideal` instances and write `experiments_database/pub_features.csv`. Same function and same convention are the **prerequisite** for these numbers to serve as an anchor: computing each side separately and then declaring the conventions identical does not count. Measured results:

| 因子 / Factor | 公开算例(n=20) / Public instances (n=20) | 自建取值 / Self-built values | 判读 / Reading |
| --- | --- | --- | --- |
| 柔性 F / Flexibility F | 0.292 ~ 1.000,中位 **0.381** / 0.292 ~ 1.000, median **0.381** | 阶梯批次基点 0.6,C 族扫 0.3 / 0.6 / 1.0 / ladder batch base 0.6; family C sweeps 0.3 / 0.6 / 1.0 | F=0.3 那一档落在公开区间内 / the F=0.3 level falls inside the public range |
| 异构 H / Heterogeneity H | 0.038 ~ 0.258,中位 **0.135** / 0.038 ~ 0.258, median **0.135** | 阶梯批次固定 0.3;矩阵批次扫 0 / 0.15 / 0.3 / 0.5 / ladder batch fixed at 0.3; matrix batch sweeps 0 / 0.15 / 0.3 / 0.5 | **0/20 达到 0.3**,是一处外推;但 H=0.15 实测 0.139 恰在公开中位附近 / **0/20 reach 0.3**, which is an extrapolation; but the measured H=0.15 of 0.139 sits near the public median |
| T̄t/T̄p | 0.040 ~ 0.118,中位 0.055 / 0.040 ~ 0.118, median 0.055 | 阶梯批次 4.0,矩阵批次 ≈1.0 / ladder batch 4.0, matrix batch ≈1.0 | 相差一到两个数量级,**有意为之** / one to two orders of magnitude apart, **on purpose** |

两处外推的性质不同,不可混为一谈:

The two extrapolations are different in kind and must not be lumped together:

- **T̄t/T̄p 是设计前提,不是取值失当。** 公开 FJSP_PT 算例里运输只占加工的百分之几,那种
  设定下车辆争用根本不值得建模——这正是本项目另立算例的理由之一。

  **T̄t/T̄p is a design premise, not a bad choice of value.** In the public FJSP_PT instances travel is only a few percent of processing, and under that setting vehicle congestion is not worth modeling — that is one reason this project builds its own instances.

- **H 是需要举证的外推。** 若收益随 H 上升,把 H 定在文献区间之上就会**抬高**主效应。这一条
  已用矩阵批次(16 格 × 四个 H 档 × 10 种子)检验:逐 H 档集成增益为
  6.12% / 5.62% / 5.95% / 4.38%(H = 0 / 0.15 / 0.3 / 0.5),Spearman(增益, H) = **−0.21**,
  **收益不随 H 上升**;H=0.15(实测 0.139,≈ 公开中位)与 H=0.3 相差不到半个百分点,故这处
  外推没有抬高主效应。详见规格 12.3.6 预测 1/2 的判定与论文 §5.5。

  **H is an extrapolation that needs evidence.** If the gain rose with H, setting H above the literature range would **inflate** the main effect. This was checked on the matrix batch (16 cells × four H levels × 10 seeds): the integrated gain by H level is 6.12% / 5.62% / 5.95% / 4.38% (H = 0 / 0.15 / 0.3 / 0.5), Spearman(gain, H) = **−0.21**, and **the gain does not rise with H**. H=0.15 (measured 0.139, ≈ the public median) and H=0.3 differ by less than half a percentage point, so this extrapolation does not inflate the main effect. See the verdicts on predictions 1/2 in spec 12.3.6 and paper §5.5.

**口径陷阱(踩过一次,记下来)**:H 必须把 `|Ω|=1` 的工序按 **0** 计入均值,不能跳过。跳过
会把公开算例的 H 中位从 0.135 抬到 0.148,而生成器是按"全部工序"算的——两边口径一旦不同,
这张表的每一行都不成立。`tools/pub_features.py` 因此**不提供**跳过的选项。

**Convention trap (stepped on once; written down)**: H must count operations with `|Ω|=1` as **0** in the mean; they must not be skipped. Skipping would lift the public-instance H median from 0.135 to 0.148, while the generator averages over "all operations". Once the two conventions differ, every row of this table fails. `tools/pub_features.py` therefore **does not offer** a skip option.

(**0/7** 为真)。**判据是后者**——只看前一列会误以为那 5 个布局能拿去跑争用档。两条性质
各排除一种还原,强度不同、覆盖面也不同:

That is `digraph_reconstructible` (5/7 true) and `corridor_reconstructible` (**0/7** true) in `fidelity.csv`. **The criterion is the latter** — looking only at the first column would suggest those 5 layouts can be run in the congestion mode. The two properties each rule out one reconstruction, with different strength and different coverage:

1. **七个布局全都不对称**。同一对位置往返时长不等(如 2-M 的 LU→m1 = 4 而 m1→LU = 8),
   这是单向导轨的必然结果。本项目的 `corridors` 是无向的、一条走廊只有一个 `time`,由它算出的
   t\* 必然对称,因此**这七张矩阵没有一张可能是本项目任何一张路网的 t\***——这正是必须开
   `ideal_dist` 旁路的原因。这一条覆盖全部 7 个。

   **All seven layouts are asymmetric.** The two directions between the same pair of locations have unequal times (for example, on 2-M, LU→m1 = 4 while m1→LU = 8), which is what a one-way guideway must produce. This project's `corridors` are undirected and a corridor has a single `time`, so the t\* computed from it is necessarily symmetric. Therefore **none of these seven matrices can be the t\* of any road network in this project** — that is why the `ideal_dist` bypass must be opened. This item covers all 7.

2. **恰好是两个"随机生成"的布局不满足三角不等式**,而四个源自真实 FMS 导轨布局的
   (4-M/5-M/6-M/8-M)全部满足。任何图的最短路闭包必然满足三角不等式,所以 3-M 与 7-M
   **连有向图都还原不出来**。这一条更强,但只覆盖 2 个。

   **Exactly the two "randomly generated" layouts violate the triangle inequality**, while the four that come from real FMS guideway layouts (4-M/5-M/6-M/8-M) all satisfy it. The shortest-path closure of any graph must satisfy the triangle inequality, so 3-M and 7-M **cannot even be reconstructed as digraphs**. This item is stronger, but it covers only 2.

由此得到一条**非事后挑选**的取舍准则,且结论比"挑掉两个"更彻底:**这七个布局无一能用于第二层
争用实验**,它们只能留在第一层退化对标里;争用实验只能用自造的受控布局(规格 12.3)。判据是
先验的数学性质,不是"哪个跑得好看"。

This yields a selection rule that is **not post-hoc**, and the conclusion is stronger than "drop two": **none of these seven layouts can be used in the second-layer congestion experiment**. They can stay only in the first-layer degenerate benchmark; the congestion experiment can use only self-generated controlled layouts (spec 12.3). The criterion is an a priori mathematical property, not "which one looks better when run".

> 这也顺带解释了 12.1 表里"显式路网:无"那一栏的真实含义——不是原作者藏了图,而是这些矩阵
> **本来就不来自任何无向走廊图**,其中两张更不来自任何图。
>
> This also explains what the "explicit road network: none" column in the 12.1 table really means — the original authors did not hide a graph. These matrices **do not come from any undirected corridor graph**, and two of them do not come from any graph at all.

## 六、转换与验收 / 6. Conversion and acceptance

转换器为 `tools/convert_public.py`(规格 12.4 第 2 项,`hf` 一族已实现),批跑器为
`tools/run_database.py`;本目录只存数据。转换的产物必须过下面三道验收,否则不许进
`json/`:

The converter is `tools/convert_public.py` (spec 12.4 item 2; the `hf` family is implemented) and the batch runner is `tools/run_database.py`. This directory stores data only. Converter output must pass the three acceptance checks below, or it may not enter `json/`:

1. **可复现**:算例头写入 `_spec`(提取文本的 SHA256 + 转换器版本 + 全部口径参数)。
   以 `_` 开头的键 `parse_instance` 会忽略,与自造算例的约定一致(规格 12.3.4)。
   另外解析器把算例头声明的 `M*J*O` 当作**独立校验源**,逐个核对机器数、工件数、工序数、
   先后关系条数(= O − J);少一行、串一行、数字粘连都会被其中一个约束抓住,故 PDF
   提取错误不会静默通过。

   **Reproducible.** The instance header writes `_spec` (SHA256 of the extracted text, converter version, and every convention parameter). Keys that start with `_` are ignored by `parse_instance`, the same convention as the self-generated instances (spec 12.3.4). The parser also treats the header's declared `M*J*O` as an **independent check source** and checks machine count, job count, operation count, and precedence count (= O − J) one by one. A missing line, a shifted line, or glued digits is caught by one of those constraints, so a PDF extraction error cannot pass silently.

2. **度量性检验**:见第五节。矩阵满足三角不等式才允许在第二层还原走廊图。

   **Metric check**: see Section 5. A matrix may be reconstructed as a corridor graph at the second layer only if it satisfies the triangle inequality.

3. **不得低于可证最优**:这是最强的一道,也是唯一能在结果层面证明转换正确的一道。
   退化档与文献是**同一个数学问题**,MILP 已证明的最优值是硬地板;若我们的解低于它,
   那不是赢,是口径不一致或实现有错。`tools/run_database.py` 把这一条做成报告顶部的
   硬性判定。

   **Must not undercut a proven optimum.** This is the strongest check, and the only one that can prove the conversion correct at the result level. The degenerate mode and the literature are **the same mathematical problem**, and an optimum already proved by MILP is a hard floor. A solution below it is not a win; it is a convention mismatch or an implementation error. `tools/run_database.py` makes this a hard verdict at the top of the report.

   > 注意退化档没有 AGV 分段,故 `validator.py` 的 (d)(e)(f)(h) 四项天然为空——**这一档
   > 的校验强度低于争用档**,"校验通过"不能充当转换正确的证据,第 3 条才能。
   >
   > Note that the degenerate mode has no AGV segments, so items (d)(e)(f)(h) of `validator.py` are empty by construction — **this mode's validation is weaker than the congestion mode**. "Validation passed" cannot serve as evidence that the conversion is correct; only item 3 can.

**公开数据给了图和弧时长,唯独没有给弧容量——因为在其原模型里车辆从不相互干扰。**
本项目补的正是这一个量。这句话是整条 add-on 路线的正当性所在,也是它与"两次模型翻译"
的区别;写进论文时应逐字保留这个界定。

**The public data give the graph and the arc durations, and give no arc capacities — because in the original model vehicles never interfere with each other.** What this project adds is exactly that one quantity. That sentence is the justification of the whole add-on route, and it is what separates the route from "two model translations". When it is written into the paper, this delimitation should be kept verbatim.

+ 时间异构 + 显式路网"。逐条核过的事实:

This one deserves its own account, because it overturns the earlier sentence in spec 12.1 that "no existing public dataset contains partial flexibility, time heterogeneity, and an explicit road network at once". Facts checked item by item:

- **部分柔性 + 时间异构**:原文 III 节"Each operation can be processed on a few different
  machines but with **different** processing times"。数据侧两处印证——Example 2 的 Table 3 是
  "工序 × 机器"工时矩阵、以 `—` 表示该机不能加工;第二组的 Table 7 用斜杠给备选,
  如 `M2(12)/M3(15)`,备选机工时**不等**。注:这两张表是从渲染图上读的,**逐格数值未逐一
  校对**,此处只支撑"有无备选、备选工时是否相等"这两个定性判断。
  **但 Table 7 已有独立机读来源可复核**(2026-08-18 核实):`TJSP-toolset` 的
  `data/benchmarks/lyu2019/jobs/` 把 14 个测试问题的工件集存成纯文本,已抽查测试问题 1 的
  三个工件,与 Table 7 **逐位相同**。故若要转它,应以该来源对账而不是重新人工转录。
  Table 3(Example 2 的工时矩阵)无此来源,仍须逐格核对;

  **Partial flexibility + time heterogeneity.** Section III of the source: "Each operation can be processed on a few different machines but with **different** processing times". Two data-side checks: Example 2's Table 3 is an "operation × machine" time matrix, with `—` meaning that machine cannot process it; the second group's Table 7 gives alternatives with a slash, such as `M2(12)/M3(15)`, and the alternative machines have **unequal** times. Note: both tables were read from rendered figures, and **the cell values were not checked one by one**. They support only the two qualitative judgments "whether alternatives exist" and "whether alternative times are equal". **Table 7 now has an independent machine-readable source that can be checked** (verified 2026-08-18): `data/benchmarks/lyu2019/jobs/` in `TJSP-toolset` stores the job sets of 14 test problems as plain text. A spot check of the three jobs of test problem 1 matches Table 7 **entry for entry**. If it is converted, reconcile against that source rather than transcribing by hand again. Table 3 (Example 2's time matrix) has no such source and still needs a cell-by-cell check.

- **显式路网**:Example 2 的 Figure 1 配 Table 4,是一张 **20×20 邻接矩阵**,给的是**相邻**点
  之间的逐段时长,正是本项目 `corridors` 所需的形式,**不是**全对最短路矩阵。
  原文措辞是 "the transit times between any two points",听着像全对,但**非对角线上大量为 0**,
  而全对最短路矩阵在连通图上不可能有非对角零元,故它只能是"0 = 不相邻"的邻接表示——
  判据用的是这个零元模式,不是原文那句措辞。这一点要紧:邻接矩阵可直接落成走廊,
  全对矩阵则会像 hf 那样只能走 `ideal_dist` 旁路;
  第二组的 Figures 10–15 是 6 张带编号节点的栅格图(9/16/16/25/25/25 节点);

  **Explicit road network.** Example 2's Figure 1 with Table 4 is a **20×20 adjacency matrix**. It gives per-segment times between **adjacent** points, which is exactly the form this project's `corridors` need, and it is **not** an all-pairs shortest-path matrix. The source wording is "the transit times between any two points", which sounds like all-pairs, but **many off-diagonal entries are 0**, and an all-pairs shortest-path matrix on a connected graph cannot have an off-diagonal zero. So it can only be an adjacency encoding with "0 = not adjacent" — the criterion is that zero pattern, not the source sentence. This matters: an adjacency matrix can be written directly as corridors, whereas an all-pairs matrix, like hf, can only take the `ideal_dist` bypass. The second group's Figures 10–15 are 6 numbered-node grid drawings (9/16/16/25/25/25 nodes).

- **边排他与本文同构**:"the layout is represented by a bidirectional network, but only one
  vehicle at a time can transit a **segment**"——段即边,故是边排他,与本文走廊排他一致;

  **Edge exclusion is isomorphic to this paper.** "the layout is represented by a bidirectional network, but only one vehicle at a time can transit a **segment**" — a segment is an edge, so this is edge exclusion, the same as this paper's corridor exclusion.

- **有参照值**:Table 5 给 Example 2 在 1–6 车下的最小/平均完工时间(129 / 92.5 / 88 / 84.5 /
  82 / 82),Table 6 给第二组 14 个问题在 3–5 档车队规模下的最小/平均完工时间与最优车数。

  **Reference values exist.** Table 5 gives Example 2's minimum/mean completion time under 1–6 vehicles (129 / 92.5 / 88 / 84.5 / 82 / 82). Table 6 gives the minimum/mean completion time and the optimal vehicle count for the second group's 14 problems at fleet sizes 3–5.

**但仍不能直接对标,两条实质原因(不是"数据难找"):**

**It still cannot be benchmarked directly, for two substantive reasons (not "the data are hard to find"):**

1. **它的冲突语义比本文多一条**:其约束 (11) "ensures that a **node** can be occupied by only
   one vehicle at a given time",即节点容量为 1,并区分 point / opposite-direction /
   road-junction 三类冲突;本文的节点是零测度通过点,只对走廊排他。故 Lyu 的模型**更紧**,
   本文方法直接跑上去等于放松了它的节点容量,可能给出在其模型下不可行的解,完工时间因而可能
   **低于**其发表值——那不是赢,是口径不同、数字不可比。这与不能直接跑 van Os & Basten (2026)
   属同一类原因(都是节点容量假设),但不是同一条约束;

   **Its conflict semantics add one constraint beyond this paper.** Constraint (11) "ensures that a **node** can be occupied by only one vehicle at a given time", i.e. node capacity is 1, and it distinguishes point / opposite-direction / road-junction conflicts. This paper's nodes are zero-measure pass-through points and exclusion applies only to corridors. Lyu's model is therefore **tighter**. Running this paper's method on it relaxes the node capacity and may produce a solution that is infeasible under Lyu's model, so the completion time may fall **below** the published value. That is not a win; the conventions differ and the numbers are not comparable. This is the same kind of reason as not running van Os & Basten (2026) directly (both are node-capacity assumptions), but it is not the same constraint.

2. **第二组的逐段行驶时间未发表,且"取单位边权"已被原文自身反证**(2026-08-18 核实)。
   Figures 10–15 只画拓扑与机器位置、不标边权,附录 B 的 Table 7 只给工件集,全文只说
   "AGVs move at a constant speed"。此前记的是"栅格规整,取单位边权是合理猜测"——**这条要改**:
   它不是未经证实的猜测,而是**有反证**的猜测。Example 2 的 Figure 1 与 Figures 10–15
   **同样画成规整网格、同样不标边权**,而它配的 Table 4 给出的相邻段时长取
   **1 / 2 / 3 三种值**(如边 1–2 为 2、边 1–6 为 1、边 3–8 为 3)。即该文的网格图是**示意图、
   不按比例**,"看上去每段一样长"在这篇论文里恰恰**不**蕴含"每段耗时相同"。
   故第二组的边权是真未知,取单位值会与该文唯一公开的段时长数据相抵触。

   **The second group's per-segment travel times were never published, and "use unit edge weights" is already contradicted by the source itself** (verified 2026-08-18). Figures 10–15 draw only topology and machine positions and mark no edge weights. Appendix B's Table 7 gives only job sets, and the text only says "AGVs move at a constant speed". The earlier note was "the grid is regular, so unit edge weights are a reasonable guess" — **that note must change**. It is not an unverified guess; it is a guess **with a counterexample**. Example 2's Figure 1 and Figures 10–15 are **drawn as the same regular grid and likewise mark no edge weights**, yet the Table 4 that accompanies Figure 1 gives adjacent-segment times of **three values, 1 / 2 / 3** (for example edge 1–2 is 2, edge 1–6 is 1, and edge 3–8 is 3). The paper's grid drawings are **schematic and not to scale**. In this paper, "the segments look equally long" does **not** imply "the segments take equal time". The second group's edge weights are therefore genuinely unknown, and taking unit values would contradict the only published segment-time data in that paper.

   > 已有先例走了这一步:van Os 的 `TJSP-toolset` 把这批布局的全部边权设为 1(见第二节的核实
   > 附注)。这个先例的价值在于**反面**——它恰好演示了"补边权"这一步是外部假设而非读到的数据。
   >
   > There is already a precedent that took this step: van Os's `TJSP-toolset` sets every edge weight of these layouts to 1 (see the verification note in Section 2). The value of that precedent is on the **negative** side — it shows that "filling in edge weights" is an external assumption, not data that was read.

   **Example 2 则是完整可转换的**(Table 3 + Table 4 + Table 5 齐全),但只有一个算例,
   且仍受第 1 条制约。

   **Example 2 is fully convertible** (Table 3 + Table 4 + Table 5 are all present), but it is a single instance and is still constrained by item 1.

结论:这一份的用途是**佐证本文的建模选择有文献先例**(双向网络 + 边排他),不是可直接对标的
基准。要真正用它,须先在本文模型里加上节点容量 1 —— 那是另一件工作,不在本轮范围。

Conclusion: this source is used to **show that this paper's modeling choice has a literature precedent** (a bidirectional network plus edge exclusion). It is not a benchmark that can be compared directly. To use it for real, node capacity 1 must first be added to this paper's model — that is a separate piece of work, outside this round.
